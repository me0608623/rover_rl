# 端到端延遲預算分解（實機量測）

> 建立：2026-07-23（車端）
> 量測工具：`scripts/latency_budget.py`（離線 bag + 推論台架）、`scripts/latency_probe.py`（線上探針）
> 資料來源：`logs/bags/deploy_20260722_164122`（718 s）、`deploy_20260716_164517`（602 s）、
> `deploy_20260715_161920`（57 s，樣本不足僅供參考）；模型 bench 在 Jetson Orin CPU 上跑。

---

## 1. 鏈路定義

```
VLP-16 掃描 ──S1──▶ /velodyne_points ──S2──▶ /rover_rl/lidar_sweep_72
                                                     │
                                                    S3（5Hz 取樣 + obs + forward + decode）
                                                     ▼
                                    RL target (v,w) ──S4a 20Hz 取樣──▶ low-pass/slew (S4b)
                                                     │
                          /rover_rl/cmd_vel_desired ─S4c─▶ VO ─▶ recovery ─▶ mux ─▶ /output/cmd_vel
                                                                                        │
                                                                                       S5（底盤致動）
                                                                                        ▼
                                                                                  odom 實測速度
```

| 段 | 名稱 | 定義（起 → 迄） |
|---|---|---|
| S1 | 感測 | LiDAR 掃描完成（`header.stamp`）→ PointCloud2 抵達本機 callback |
| S2 | 點雲前處理 | 點雲抵達 → `lidar_sweep_72` 發布（含 10 Hz timer 取樣 + sweep 計算） |
| S3 | 策略推論 | sweep 抵達 → RL 決策完成（含 5 Hz 取樣造成的 obs 老化 + obs build + forward + decode） |
| S4 | 速度指令 | RL target → `/output/cmd_vel`（20 Hz 取樣 + 低通/slew 相位 + VO/recovery/mux 各 hop） |
| S5 | 致動 | `/output/cmd_vel` → 底盤實際速度（odom 量到） |

## 2. 分段量測結果

**通道說明**：控制穩定性由**角速度 ω 通道**決定（v 通道等速直行時訊號太平、互相關不可信，
見 `docs/2026-06-08_ESCALATION_給PC端_延遲感知重訓.md`）。低通係數 v/ω 不同故 S4b 分列。

| 段 | 分項 | p50 (ms) | p90 (ms) | 狀態 | 依據 |
|---|---|---|---|---|---|
| **S0** | 掃描相位（點被掃到 → 該圈時戳） | 50（0–100 均勻期望） | 100 | ✅ 分析式 | driver `timestamp_first_packet: false` → 時戳為掃描**結束**，圈內各方位量測比時戳舊 0–100 ms |
| **S1** | 點雲時戳 → 抵達本機 | **23.5** | 24.3 | ✅ 已量 | 探針 60 s，n=595（driver 在 192.168.3.13，兩機 chrony 同步） |
| **S2** | 點雲 → sweep（含 10 Hz 取樣） | **54.9** | 71.2 | ✅ 已量 | 探針，n=595 |
| **S3a** | sweep 老化（5 Hz 取樣 over 10 Hz sweep） | **22.9** | 92.4 | ✅ 已量 | policy status `sweep_age_ms`，n=300 |
| **S3b** | 推論 tick 全程（車姿查詢+子目標+obs+forward+decode） | **19.4** | 29.1 | ✅ 已量 | policy status `infer_ms`，n=300 |
| **S3b′** | 其中純網路前向 v3f（79D RNN） | 3.1 | 13.1 | ✅ 已量 | bench，300 次，obs 0.04 + fwd 3.03 + decode 0.07 |

### S4c 逐 hop 明細

| hop | 節點 | bag A（07-22, 718 s） | bag B（07-16, 602 s） |
|---|---|---|---|
| `cmd_vel_desired` → `cmd_vel_recovery_in` | vo_safety | p50 26.2 / p90 77.3 ms（pass 82%） | p50 12.6 / p90 62.9 ms（pass 91%） |
| `cmd_vel_recovery_in` → `input/nav_cmd_vel` | recovery_supervisor | p50 27.3 / p90 44.9 ms（pass 97%） | p50 14.4 / p90 15.4 ms（pass 99%） |
| `input/nav_cmd_vel` → `output/cmd_vel` | cmd_vel mux | p50 3.8 / p90 17.6 ms（pass 70%） | p50 2.2 / p90 30.9 ms（pass 92%） |
| （交叉驗證）`desired` → `nav_cmd_vel` 直測 | — | p50 56.0 ms ≈ 26.2+27.3 ✓ | p50 26.9 ms ≈ 12.6+14.4 ✓ |

> `pass` = 數值原樣通過的比例；其餘為 VO/recovery 改寫（介入）樣本，本表只統計未改寫者。
> 兩 bag 差異來自當日 VO/recovery 負載與 CPU 佔用；**取較保守的 bag A 進入預算**。

> ⚠ 但互相關並非在所有訊號上都可靠：該次 teleop 錄製訊號偏慢、相關峰過寬，argmax 誤報 550 ms。

## 3. 累計端到端延遲

### 3.1 policy 決策 → 輪子響應（閉迴路等效死時間）

| 通道 | S3b | S4a | S4b | S4c | S5 | **累計** |
|---|---|---|---|---|---|---|
| ω（控制穩定性主導） | 19.4 | 25 | 50 | 58 | 200 | **≈ 352 ms** |
| v | 19.4 | 25 | 117 | 58 | 200 | **≈ 419 ms** |

→ **ω 通道等效死時間 352 ms ≈ 1.8 個控制步**（control_dt = 200 ms）。

### 3.2 完整端到端

| 起點 | 組成 | p50 合計 |
|---|---|---|
| **點雲時戳 → 輪子響應**（純資料路徑，全部實測/分析、無估計成分） | S1 23.5 + S2 54.9 + S3a 22.9 + S3b 19.4 + S4a 25 + S4b 50 + S4c 58 + S5 200 | **≈ 454 ms（ω）** |
| **雷射打到障礙物 → 輪子響應**（含掃描相位 S0） | 上列 + S0 50 | **≈ 504 ms（ω）** |

線速度通道把 S4b 換成 117 ms → 521 / 571 ms。

> **論文引用建議用 454 ms（ω，點雲時戳起算）**：此值每一項都有實測或解析依據。
> 若要主張「物理事件 → 動作」則用 504 ms，並註明其中 50 ms 為掃描相位之期望值。

## 4. 與延遲感知訓練所模擬區間之對照

訓練端設定（`models/tcadapt_60k_deploy_info.yaml`、`models/**/full_args.json`）：

| 項目 | v3f 定版 `sa5_v3f_tcadapt_60000`（部署中） | v3h clean baseline `sa6_v3h_nonoise_nodr` | 實機量測 |
|---|---|---|---|
| 致動延遲 `actuator_delay_range` | **[0, 1] 步 = 0–200 ms**（均勻，期望 100 ms） | [0, 0] = 0 | **200 ms**（S5，r=0.99） |
| 馬達一階 lag `actuator_motor_lag` | **0.5** | 0.0 | 對應實機低通 α（ω 0.5 / v 0.3）+ 底盤動態 |
| 觀測延遲 `obs_delay_steps` | **[0, 0] = 0 ms**（訓練端刻意關閉，「sin 波兇手」） | [0, 0] | **S0+S1+S2+S3a = 151 ms（實測）** |
| 控制週期 | 0.2 s | 0.2 s | 0.2 s ✓ 對齊 |

（觀測延遲實機值 = S0+S1+S2+S3a = 50+23.5+54.9+22.9 ≈ **151 ms**，實測，非估計。）

### 對照結論

1. **致動延遲：實機落在訓練 DR 的上緣極值。** 訓練 [0, 200] ms 均勻抽樣，期望值只有 100 ms；
   實機穩定在 200 ms（= 分布最大值）。policy 平均而言是在「比實機快一倍」的世界裡學的，
   只有抽到上緣的那批 episode 才對應真實情況。
2. **觀測延遲：訓練為 0，實機實測 151 ms — 這是目前最大的未建模項。**
   訓練端因「obs_delay 造成 sin 波振盪」而關閉此項，但實機的感知路徑延遲並不會因此消失，
   它以「policy 看到的是 0.15–0.2 s 前的世界」的形式進入閉迴路。
3. **總量對照**：實機 ω 通道 policy→輪子 352 ms（1.8 步）、含感知前段 454–504 ms（2.3–2.5 步）；
   訓練所模擬者為致動側 0–200 ms（0–1 步）+ motor lag。
   **實機閉迴路總延遲高於訓練分布上緣**，方向與 2026-06-08 觀察到的 0.2–0.43 Hz 極限環一致
   （delay/control_dt ≥ 1 即進入相位裕度惡化區）。
4. **`actuator_motor_lag=0.5` 的時間常數語意待 PC 端確認**：若為每控制步的一階係數
   （`v_applied += 0.5·(v_cmd − v_applied)`，dt=0.2 s），等效時間常數 0.2 s，則訓練側總延遲
   可達 ~400 ms，會與實機 352 ms 相當接近；若為其他定義則結論不同。**此列在確認前不得引用。**

## 5. 復現步驟

S1/S2 需 LiDAR 在線；S3a/S3b 另需 policy 在 `nav` 模式實際推論。**車靜止即可量，不必移動**
（只有 S5 需要車有轉向動作，而 S5 用既有 bag 離線算即可）。
安全作法：量 S3 時把 policy 輸出導到無人訂閱的 topic
（`-p topic_cmd_vel:=/latency_probe/cmd_sink_no_chassis`），指令不可能到底盤。

```bash
# 1) 起 VLP-16 driver —— ⚠ 此 Jetson 上只有 velodyne_msgs，沒有 driver 套件；
#    /velodyne_points 由另一台主機經 zenoh 發布，故 driver 要在該台起（依現場既有流程）。
#    本機確認有在發：ros2 topic info /velodyne_points -v → Publisher count ≥ 1

# 2) 起前處理（本機）
source /opt/ros/humble/setup.bash && source ~/rover_rl/setup_env.sh
source ~/rover_rl/install/setup.bash
ros2 run rover_rl_inference lidar_preprocessor &

# 3) 要一併量 S3a/S3b 就照常起棧（idle → 給 goal 進 nav 才會推論）
deploy_rl initial_mode:=idle

# 4) 跑探針 60 秒，結束自動印總表
python3 ~/rover_rl/scripts/latency_probe.py --secs 60
```

離線段（S4c / S5 / 推論台架）復現：

```bash
python3 ~/rover_rl/scripts/latency_budget.py --bag ~/rover_rl/logs/bags/deploy_20260722_164122
python3 ~/rover_rl/scripts/latency_budget.py --bench ~/rover_rl/models/sa5_v3f_tcadapt_60000.ts
```

### 量測有效性須知

- **S1 需時鐘同步（本次已驗證）**：`header.stamp` 由 velodyne driver 打，driver **不在本機**
  （跑在 `humble@192.168.3.13`，點雲經 zenoh 過來）。量測當下確認：本機 chrony 對 time4.google.com
  同步（誤差 53 µs），該台 chrony 以本機（192.168.3.14）為上游 stratum 3 → 兩機同步，S1 有效。
  探針另會自動偵測異常差值並印警告。S2/S3 全走本機 monotonic 時鐘，不受此限。
- **S0 來自 driver 時戳語意**：`VLP16-velodyne_driver_node-params.yaml` 的
  `timestamp_first_packet: false` → 整圈以**最後一個封包**時刻打戳，故圈內各方位的量測比時戳舊
  0–100 ms。若日後改為 `true`，S0 的符號要反過來（點雲會比時戳新），此列必須重算。
- **bag 時戳為錄製端收訊時間**，S4c 因此含 recorder 佇列抖動；p50 受影響小，p90/max 會被放大。
- **S5 需車有轉向動作**：ω 訊號標準差過低時互相關不可信（bag C 的 r=0.34 即此情形）。
- policy status 自 2026-07-23 起新增 `infer_ms` / `sweep_age_ms` 兩欄（純觀測、不參與控制），
  重啟部署後即會寫進 bag 與 TUI 資料源，供之後每次實驗自動累積 S3 樣本。
