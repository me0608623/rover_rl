### speed_rate 的處理（依你們 §4 的要求）

車端的時間膨脹是把**動作上限** ×rate（`act_eff`）、感知量 ×(1/rate)。因此：

```python
v_base = self._int_v_pf * rate        # 積分器存 policy-frame，乘回 act_eff 的實體尺度
cmd_v, cmd_w, accel = decode_logits_to_cmd(logits, current_linear_vel=v_base, params=act_eff, ...)
self._int_v_pf = cmd_v * inv          # 存回未縮放值
```

數學上與「存未縮放、送出才縮放」等價（整條鏈對 rate 齊次），但存 policy-frame 讓
`speed_rate` 熱調（`ros2 param set`）時不會有尺度錯亂。

### reset 時機

`_set_target_stop()` 是所有強制停車的單一出口，語意上「issued = 0」，所以積分器一併歸零，
自動涵蓋你們列的四種情境。`_reset_act_hist()` 則涵蓋新 goal / 切模式 / 換模型 / RNN reset。

## 3. 回答你們的問題：穩態尺度 vs 含延遲的瞬時值

### 先講一個前提發現：**這批資料裡不存在穩態窗口**

依你們建議的判別法（`sent_w` 同號、幅值穩定 ≥1.5 s，比較末段比值），我掃了全部 9 段
有效資料：**穩定窗口數 = 0**。在車真的在走的每一段裡，ω 命令從來沒有連續 1.5 秒
維持在同一幅值（±15%）內。policy 每拍都在改 ω 且常打滿 slew（見 8/17 文件 §7.2）。

所以「末段比值」這個方法在這批資料上無法套用，改用參數化擬合。

### 擬合模型

```
a[n] = α · a[n-1] + (1-α) · k · s[n-L]
  L = 純延遲（互相關取最大 r）   τ = -dt / ln(α)   k = 穩態增益
```

| 段 | rate | 純延遲 L | τ | **穩態增益 k** | R² |
|---|---|---|---|---|---|
| 20:27:13 | 1.0 | 400 ms | 358 ms | 26% | 0.81 |
| 20:28:36 | 1.0 | 400 ms | 460 ms | 46% | 0.89 |
| 20:33:48 | 1.0 | 400 ms | 401 ms | 63% | 0.89 |
| 20:41:29 | 1.0 | 350 ms | 770 ms | 31% | 0.92 |
| 20:36:48 | 0.6 | 450 ms | 665 ms | 58% | 0.94 |
| 20:37:43 | 0.6 | 400 ms | 399 ms | 72% | 0.94 |
| 20:38:40 | 0.6 | 400 ms | 334 ms | 83% | 0.96 |
| 20:39:38 | 0.6 | 400 ms | 80 ms | 99% | 0.96 |
| 20:49:43 | 0.6 | 400 ms | 91 ms | 94% | 0.93 |
| **均值 rate=1.0** | | **388 ms** | **497 ms** | **42%** | 0.88 |
| **均值 rate=0.6** | | **410 ms** | **314 ms** | **81%** | 0.94 |

### 結論

1. **純延遲 ~400 ms 與命令幅值無關**，各段高度一致（350~450 ms），
   與你們從 `lag_ms` 算的 p90 = 400 ms 吻合。這一項可以直接當常數用。
2. **原本回報的 28~44% 是未補償的瞬時比值**，低估了穩態尺度。扣掉延遲與一階 lag 後，
   rate 1.0 的穩態增益是 **42%**。
3. **但 42% 仍遠低於訓練假設的 0.9~1.1**，所以**尺度問題是真的存在，不只是延遲**。
4. ⚠️ **關鍵：k 會隨命令幅值變化**。rate 1.0（平均 |ω| 0.585、峰值 1.2）→ k=42%；
   rate 0.6（平均 |ω| 0.265~0.433、上限 0.72）→ k=81%，其中兩段甚至到 94~99%。
   底盤 `profile_omega_max = 1.2`，rate 1.0 時命令長時間貼著這個上限 → 飽和。

### 對訓練端的建議

**不要只把 `actuator_velocity_scale` 從 0.9~1.1 改成 0.42**——那會在小命令區間過度懲罰
（實測小命令時 k 接近 0.9~1.0，原設定其實是對的）。比較貼近實車的做法是二選一：

- (a) 保留 `actuator_velocity_scale ≈ 0.9~1.1`，但**加上飽和**：命令超過 ~0.7 rad/s 後
  增益開始下滑，到 1.2 rad/s 時只剩約 4 成；並把 `actuator_delay_range` 中心往上調
  （你們也算出 p50 300 ms，建議 `(1, 2)` 或 `(1, 3)`）、一階 lag τ 用 ~350 ms。
- (b) 直接把 `max_angular_vel` 降到底盤跟得動的範圍（~0.7 rad/s），讓 policy 不會學會
  叫出做不到的轉速。這比較像治本，但會改變動作空間、需要重訓且與既有 checkpoint 不相容。

車端補充一個佐證：**降 speed_rate 到 0.6 之後 k 從 42% 升到 81%**，而 0.6 剛好把 ω 上限
壓到 0.72 —— 這與「飽和點在 0.7 附近」的推測一致。

## 5. 回問：obs 的 speed 維度是否也該改成 issued？

你們 §附錄提到找不到 obs `speed` 那一維的對應函式，但指出「`_current_velocity` 就是寫進
剛體的值，任何物理讀取在數值上都等於它」。

那同一個論證應該也適用於 obs：訓練時 obs[1]（speed_norm）讀到的是剛體速度 = issued；
**實車上 obs[1] 目前餵的是 odom 量測**，而量測與 issued 在實車差很多（v 跟隨 96~126%、
ω 只有 42~81%）。

- 若要完全對齊訓練語意，obs 的 ego 速度三維（accel / speed / omega）也該改用 issued。
- 但這會讓 policy **完全看不到底盤實際狀態**，在真實有滑動/打滑時失去唯一的回授。

這一題車端**沒有動**，等你們判斷。若要改，希望連同 `last_accel` 與 ω 一起給明確指示。
