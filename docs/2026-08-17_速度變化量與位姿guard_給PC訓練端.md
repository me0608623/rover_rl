# 2026-08-17 車端回饋：速度變化量實測 + pose_jump_guard 誤觸 + speed_rate 降 0.6

> 車端（Jetson / CampusRover）→ PC 訓練端。模型 `sa4_r2_c6400_83d_k8.ts`（83D, K=8）。
> 資料為地面實跑兩段 routing 導航，非架空。

## TL;DR

1. **decoder 沒有違規，但「指令序列」的相鄰跳變會超過 a_max·dt。** 原因是
   `next_v = clip(v + accel·dt)` 的基準 `v` 餵的是**實測 odom 速度**、不是上一拍 issued v。
   → 需要 PC 端確認訓練端 `process_actions` 的基準到底是哪一個（**最重要的一題，見 Q1**）。
2. **`pose_jump_guard` 在正常行駛下會誤觸**：門檻 `v_max 1.0 × dt × margin 1.5 = 0.30m`，
   實測每拍位移 0.298~0.347m，兩段共觸發 5 次，每次全停 0.6~0.8s 並 reset RNN + 清 act_hist。
3. **ω 每一拍都打滿 slew 上限**（Δω p95 = 0.600 = `3.0 × 0.2`），左右翻轉 ~36 次/分，
   而底盤 ω 只跟到 28~44%。晃頭是角向且底盤跟不上，與既有 gap #2 一致。
4. 車端已把 `speed_rate` 由 1.0 降為 **0.6**（違反 8/17 定案，理由與代價見 §5）。

## 2. 單步變化量（5 Hz 決策步）

契約上限：Δv ≤ `a_max·dt` = 0.10 m/s、Δω ≤ `α_max·dt` = 0.60 rad/s。

| 量 | 段 1 平均\|Δ\| / p95 / max | 段 2 平均\|Δ\| / p95 / max | 超 0.10 或 0.60 |
|---|---|---|---|
| Δ rl_v（=送出） | 0.097 / 0.901 / **0.965** | 0.056 / 0.166 / **0.909** | 段1 8/101 (7.9%)、段2 12/142 (8.5%) |
| Δ rl_w（=送出） | 0.365 / **0.600** / 1.067 | 0.365 / **0.600** / 1.000 | 0 次（見下） |
| Δ act_v（實測） | 0.037 / 0.082 / 0.094 | 0.034 / 0.106 / 0.241 | — |
| Δ act_w（實測） | 0.314 / 0.636 / 0.725 | 0.190 / 0.647 / 0.809 | — |

### 2.1 Δv 超上限的機制（不是 bug，是基準定義）

`action_decoder.py:108`：

```python
a_hi = min(+a_max, (+v_max_pos - v) / dt)
a_lo = max(-a_max, (-v_max_neg - v) / dt)
next_v = clip(v + accel * dt, -v_max_neg, +v_max_pos)
```

`policy_node.py:1288` 傳入的 `current_linear_vel=v` 是**實測 odom 速度**。
所以「相對實測基準」每一步都 ≤ 0.10 m/s（合規）；但**相對上一拍 issued v** 就會放大，
因為實測 v ≠ 上一拍 issued v。逐筆對照（段 2，排除 guard 停車段）：

| t_rel | 上一拍送出 → 本拍送出 | Δ | 當時實測 v | 說明 |
|---|---|---|---|---|
| 30.53 | 0.499 → 0.284 | **−0.215** | 0.433 | ≈ 實測 − 0.1（滿減速） |
| 15.79 | 0.442 → 0.265 | −0.177 | 0.342 | 同上 |
| 11.38 | 0.736 → 0.909 | +0.173 | 0.836 | ≈ 實測 + 0.073 |
| 30.93 | 0.187 → 0.021 | −0.166 | 0.040 | 同上 |

每一筆都能用「實測 v ± a_max·dt」解釋。**這就是 Q1 要問的東西。**

### 2.2 Δω 沒有違規，但完全貼在 slew 上限

兩段的 Δω p95 都剛好 = 0.600 = `act_max_angular_accel 3.0 × dt 0.2`，代表 policy 每一拍
想要的 ω 變化都比 slew 允許的更大、一路被 slew 擋著。max 1.000/1.067 那筆是車端統計時把
「無目標的停車列（ω=0）」當前一拍造成的假象，實際 `w_prev=0.4 → 1.0` 恰為 +0.6，合規。

## 3. pose_jump_guard 誤觸（車端新加的保護，非訓練端問題，但會污染資料）

`logs/deploy_20260817_202512.log` 全部 5 筆：

```
位姿跳變 guard[rejected]：位移跳變 0.298m > 上限 0.295m (v_max 1.0 × dt 0.197 × 1.5)
位移跳變 0.301m > 上限 0.300m (v_max 1.0 × dt 0.200 × 1.5)
位移跳變 0.311m > 上限 0.296m
位移跳變 0.347m > 上限 0.300m
位移跳變 0.346m > 上限 0.300m
```

觸發後（`policy_node.py:1080-1091`）：`runner.reset()` + `_reset_act_hist()` +
`cmd_filter.reset()` + `_set_target_stop()`。實測後果（段 2）：

| t_rel | 停車時長 | 造成的 Δ rl_v |
|---|---|---|
| 11.53 | 0.80 s | 0.909 → 0.000（−0.909），恢復時 0.000 → 0.647 |
| 14.53 | 0.60 s | 0.486 → 0.000，恢復時 0.000 → 0.513 |

段 2 的 `rnn_resets` 在 52 秒內遞增 **8 次**。門檻用的是 `act_max_linear_velocity=1.0`，
但底盤實測 v 可達 1.019、加上 NDT 修正 map→odom 會整體平移，0.2s 走 0.30~0.35m 很常見。
**車端傾向把 `pose_jump_margin` 1.5 → 2.0，或門檻改用底盤實測上限 1.5 m/s。**
對 PC 端的意義：**這兩段資料裡的 RNN hidden 不是連續的**，分析 act_hist / 延遲時要把
guard 事件前後幾拍剔除（時間點見上表與 log）。

## 5. 給 PC 端的問題（依重要度）

**Q1（最重要）** 訓練端 `discrete_differential_drive.process_actions` 積分線速度時，
基準 `v` 是「上一拍 **applied/issued** 速度」還是「當拍**量測**速度」？
車端目前餵**量測值**（`policy_node.py:1289`）。若訓練端用的是 issued v，則車端每一拍的
基準都與訓練不同（實測 v 跟隨率 96~126%、ω 只有 28~44%），這會直接影響 83D 的
`action_stack` 語意與整條指令序列的平滑度。要改成 issued v 的話，車端要不要同步改？

**Q2** `act_max_angular_accel=3.0` 是訓練值。實測 Δω 的 p95 完全打滿 0.6，
即 policy 想要的角速度變化率長期超過 slew。訓練端統計的 Δω 分布也是貼在上限嗎？
若訓練時很少打滿、實車卻一直打滿，代表 obs 端（goal 方位/車姿）比訓練更抖。

**Q3** 底盤 actuator 現實：ω 跟隨率 28~44%（送出 0.585 → 實測 0.164）、
整段互相關延遲 **401 ms**（r=0.92, v 通道）。訓練端是否可以加一階 ω 一階延遲/飽和模型？
現在 policy 是對著「它以為會照做」的底盤在下命令。

**Q4** `speed_rate=0.6` 的 act_hist 偏差（§4 代價 1）能否接受？
或 PC 端能否提供以 rate<1 訓練 / 對 act_hist 正規化不敏感的 checkpoint？

**Q5** `allow_reverse=false` 但 policy 明確要求倒車（8 次 `-0.200` 被夾成 0，
`-0.200` 正好是 `v_max × reverse_velocity_scale`）。訓練時倒車出現頻率多高？
若倒車是脫困的必要手段，車端要不要在確認安全後開 `allow_reverse:true`？
