## 二、VO goal 導向項 — 解「只停不繞」（實作）

**症狀**：前方有障礙時 VO 幾乎都停、不繞。

**根因兩層**：
1. RL obs 障礙欄補 0 → RL 只會直走、從不下繞行指令；VO 成本原本只 `w_v·Δv²+w_w·Δω²`
   （貼近 RL 直走）→ 直走被擋時最貼近解就是慢→停。
2. 參數過保守：`horizon 1.2`/`margin 0.15` 讓所有轉彎弧線 rollout 都判會撞，只剩停車可行。
   數學上只要有任一轉彎弧線可行，其成本就 < 停車（停車成本=w_v·v_des²≈1.0）→「總是停」必然是
   轉彎弧線全被判不可行。

**修法（兩波疊加，在 `vo_layer.py`/`vo_safety_node.py`/`vo_params.yaml`）**：
1. 鬆綁參數讓繞行弧線可行：`horizon 1.2→0.8`、`margin 0.15→0.10`、`w_w 0.3→0.15`。
2. 加 goal 導向成本項：`cost += w_goal·heading_err²`，`heading_err` = 弧線 rollout 終點朝向 vs
   終點→goal 方位的夾角。直走被擋時改偏好「繞過障礙又重新對準 goal」的弧線，且挑朝 goal 那一側繞。

**安全設計（不亂搶 RL）**：
- goal 項只在「有近障→跑候選搜尋」時作用；無近障時 VO 仍零偏差放行 RL（已模擬驗證 v=1.0 w=0）。
- `w_goal` 必須 < `w_v`（yaml 預設 0.4）：路徑暢通時 RL 仍勝出，只有直走被擋、選繞行側時 goal 主導。
- goal 來源：訂 `/rover_rl_policy/status` 的 body-frame `goal_dist`/`goal_ang_deg`（policy 已走正確
  TF），每拍配當下 odom_yaw 反推 odom 座標，不混用 map/odom。逾時 1.5s/待命無 goal → 自動關退回純貼近 RL。
- rollout 重構：`_rollout_min_ttc`→`_rollout` 回 `(ttc, ex, ey, eyaw)`；status JSON 加 `w_goal`/`goal_active`。

**天花板（要 PC 端）**：正面對衝的人 → 所有前向弧線外推都會撞 → VO 仍只能停讓它過（正確安全行為）。
真正大幅繞行需把動態障礙餵進 RL obs。

## 三、系統辨識翻盤 + 低 step v3 蛇行歸因

### 3.1 sysid 翻盤：底盤角速度其實 ~100% 跟隨

用 `scripts/sysid_record.py`（被動錄 `/output/cmd_vel`↔`/odom` 角速度，人手搖桿開 90s）辨識 ω 通道：
- **靜態增益 K≈1.0**（命令 0.34→實測 106%、0.38→102%）、**死區僅 0.056 rad/s**——可信。
- 舊說「ω 跟隨率僅 12~35%」是**在 bang-bang 飽和命令上量的假象**：命令翻太快被死時間+平均錯位吃掉，
  非底盤增益不足。底盤其實是「增益 1.0 + 純延遲」的乾淨對象 → Smith-predictor 反而好做。
- ⚠ 死時間/τ 仍未量準：此趟手開太順太慢（命令主頻 0.01Hz），cross-corr 0~800ms 全平 → 報的
  550ms / τ=76ms 都不可信。要量死時間需快速左右抖搖桿(~1-2Hz)或對 `/output/cmd_vel` 灌方波。
- 量測坑：①底盤實收是 `/output/cmd_vel`（rover_driver remap），mux 靠搖桿按鈕切模式，主動灌
  `/input/nav_cmd_vel` 不在 nav 模式會被擋。②原地轉受 in-place 黏滑摩擦污染，要邊走邊轉。

### 3.2 低 step v3 在 lag=0 仍震 → 病根偏 policy 欠訓練

- `sa1_v3e_60000`：9s 乾淨短程、**lag_ms 中位數=0**、底盤跟隨 v98%/w104%，照樣 sin 波蛇行
  （`rl_w` ±0.6 砸到底=bang-bang、~0.31Hz、車頭 ±20° 擺）。**無可測延遲卻仍震 → 震盪源在 policy 自身**
  （欠訓練的 heading 控制是 bang-bang，非比例）。
- `sa2_v3c_90000`：同 signature 但更糟，全程卡 ~20m 沒前進，後段 ~90s 凍結（odom/sweep 斷流→watchdog
  發 0，屬 odom 間歇斷流，非模型蛇行）。
- → 要平滑優先用訓練更久的 v3（`sa2_v3e_240000` / `sa3_v3c_240000`）或跟 PC 要更高 step。
  `cmd_delay_comp` 對此無用（既有 A/B 結論：補償擺幅不降、頻率反升）。

### 3.3 既有結論複述
車端 cmd_delay obs 預測補償救不了 0.42Hz 舞龍舞獅，已 escalate PC 端「延遲感知重訓」
