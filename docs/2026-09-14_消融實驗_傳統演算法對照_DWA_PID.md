# 消融實驗：傳統演算法（DWA / PID / MPPI）對照 RL policy

> 建立 2026-09-14，2026-09-16 加入 MPPI（取樣式 MPC）與 `baseline_arm`。
> 目的：論文消融實驗——比較各演算法**在相同 A↔B 往返點位的行駛路線與速度變化**。
> 分支 `baseline-ablation-dwa-pid`。

## 設計原則：只換控制器，其餘完全相同

四種條件共用同一套 NDT / costmap / routing / LV-DOT / diag_logger / pingpong_test，
**只換「誰在發 `/input/nav_cmd_vel`」**，確保比較公平（同 TF、同地圖、同測試協定、同記錄管線）。

演算法本身**不是新寫的**，是 `campusrover_move` 裡早就在這台車跑過的既有節點：

| controller | 節點 | 行為 |
|---|---|---|
| `rl`（預設） | `policy_node` | 現況，可疊 MPPI / VO / ORCA / Recovery |
| `dwa` | `campusrover_move/dwa_planner` | 軌跡取樣 DWA + costmap 靜態避障 |
| ~~`pid`~~ | `campusrover_move/path_following` | 純路徑跟蹤，零避障。**2026-09-16 移出實驗矩陣**（見下） |
| `pid_vo` | `path_following` → `vo_safety_node` | 純跟蹤 + VO 動態避障 |
| `mppi` | `campusrover_move/mppi_planner`（原生 path 模式） | 取樣式 MPC：230 rollout × 3.5s 前瞻 + costmap 靜態避障 |

**最終實驗矩陣（2026-09-16 定案）：`dwa` / `mppi` / `pid_vo` / `rl` 四組。**
測試場景以**行人等動態障礙**為主，各組角色：

| 組 | 避障資訊來源 | 性質 |
|---|---|---|
| `dwa` | costmap（行人的**當下位置**） | 反應式，經典取樣式局部規劃（1997） |
| `mppi` | costmap（同上） | 反應式，取樣式 MPC（現代對照） |
| `pid_vo` | LV-DOT 追蹤的**速度**（`tracked_obstacles`） | **預測式**，VO half-plane |
| `rl` | 72-bin LiDAR sweep（當下位置，obs 障礙欄補 0） | 學習式 |

**`pid`（零避障）已移出矩陣**，理由：
`path_following` 在 `enable_costmap_obstacle:=false` 下 `CostmapCallback()` 開頭就 return
（`path_following.cpp:886`），完全不讀 costmap，路中間有人也不減速不繞行。
它的結果只反映「障礙物擺哪裡」（擺 path 上 → CR≈100%，擺 path 外 → SR≈100%），
不反映任何演算法特性；唯一價值「標定場景難度」用障礙物與 path 的幾何關係描述即可，
不需要真的開車去撞，而且實車跑保證碰撞的組合有風險。
程式碼保留（`controller:=pid` 仍可用），日後若審稿人要求「無避障基準」再跑。

- 速度上限**對齊 RL 的實體上限**，不是底盤上限（2026-09-16 修正，見下方「速度上限對齊」）
- 非 `rl` 時 `policy_node`/`bev`/`mppi`/`orca`/`recovery` 一律不啟，避免搶發 cmd_vel
- `lidar_preprocessor` **所有 controller 都啟**（理由見下方「踩過的坑」#3）

## ⭐ 速度上限對齊（2026-09-16 修正，做錯這件事整批數據作廢）

原本 baseline 硬編「底盤真實上限 v=1.0 / ω=1.2」，**那不是 RL 實際跑的速度**。
RL 的實體上限是：

```
實體 v = act_max_linear_velocity  × speed_rate
實體 ω = act_max_angular_velocity × speed_rate      (policy_node.py:117-118)
實體加速度 = act_max_*_accel × speed_rate            (policy_node.py:1328/1332)
```

`speed_rate` 是「時間膨脹」，**同時**縮線速度、角速度與加速度。各 checkpoint 差很多：

| RL config | speed_rate | 實體 v | 實體 ω | 對照 1.0/1.2 的落差 |
|---|---|---|---|---|
| `sa1r1` | 1.00 | 1.00 | 1.20 | 一致 |
| `e2e` / `sa5r2c250` | 0.70 | 0.70 | 0.84 | baseline 快 43% |
| `v3h` | 0.65 | 0.65 | 0.78 | 快 54% |
| `sa4r2` / `sa4r3` | 0.60 | 0.60 | 0.72 | 快 67% |
| `v3f` | 0.55 | 0.55 | 0.66 | 快 82% |
| `v3c` / `v3e` / `w1c10` | 0.50 | 0.50 | 0.60 | 快 100% |
| `policy_params.yaml` | 0.35 | 0.35 | 0.70 | 快 186% |

**而且 `deploy_rl_shell` 啟動 RL 時會再問一次 speed_rate（Enter=0.6）覆寫 yaml**
→ 真正的值是那次啟動當下決定的，事後只能從 `diag_*_params.json` 的 `speed_rate` 查。

用法（`deploy_baseline_shell` 會互動詢問，也可直接帶參數）：

```bash
# 自動換算（推薦，不會手算錯）
deploy_baseline_shell controller:=mppi align_rl_config:=sa4r2
# RL 那次啟動有現場改 speed_rate 就補上
deploy_baseline_shell controller:=dwa align_rl_config:=sa4r2 align_speed_rate:=0.7
# 直接給數字
deploy_baseline_shell controller:=pid baseline_max_v:=0.7 baseline_max_w:=0.84
```

啟動時 log 會印出這次用的上限與來源，**跑之前先確認那一行**。

實作在 `deploy_full.launch.py` 的 `resolve_baseline_limits`（Part 11c-2），算好後用
`SetLaunchConfiguration` 廣播給 dwa / pid / mppi / `baseline_arm` **四處共用同一組值**——
這點很重要：dwa/pid 的 `parameters` 會在 arm 時被 service 的 `speed_parameter` 覆寫，
兩邊若各自填數字會悄悄不一致。

事後查證：`diag_*_params.json` 在 baseline 下改抓對應 planner 節點的參數
（`policy_node_name` 自動指向 `dwa_planner`/`path_following`/`mppi_planner_node`），
所以兩組的 CSV sidecar 都查得到各自的速度上限。

### ⚠ 加速度目前沒有對齊

| | 線加速度 | 角加速度 |
|---|---|---|
| RL（sa4r2, rate 0.6） | 0.30 m/s² | 1.80 rad/s² |
| dwa | 無輸出限制（`max_linear_acceleration: 5.0` 只是速度取樣範圍） | 同左 |
| mppi | 1.5 m/s² | 10.0 rad/s² |
| pid | `path_following` 內部步進 | 同左 |

**baseline 起步會比 RL 猛**，畫「速度變化」曲線時這會直接反映出來。

**✅ 已定案（2026-09-16）：維持現況，在論文中說明差異，不做自動對齊。** 理由：
- 速度上限是「能力邊界」，四組必須統一，否則「誰先到」失去意義 → 已對齊。
- 加速度平滑屬於各控制器自身的設計：RL 的 0.5 m/s² 是**訓練分布約束**（底盤真實
  `acc_max=1.2`，見 `driver_chgh.yaml`），DWA 的取樣範圍、MPPI 的 rollout 動力學
  同樣是各自演算法的一部分。硬壓成同一個數字會改變演算法本身的行為，
  比較的就不再是「這個方法」而是「被閹割過的這個方法」。
- dwa 技術上也壓不了：`max_linear_acceleration` 只影響速度取樣範圍，不限制輸出。

論文寫法建議：在實驗設定表列出「速度上限（統一）」與「加速度（各方法原生值）」兩列，
並在速度曲線圖的說明中指出起步段差異來自加速度設定而非避障行為。
啟動 log 會在用 `align_rl_config` 時把兩邊數字一起印出來，每次實驗都留下記錄。

## 出圖：論文數據四行指令

四組跑完後，同一個 `pingpong_metrics_<session>.csv` 餵給三支腳本就能拿到全部圖表。
（多個 session 的話 `pingpong_report` 可吃多檔；前兩支一次吃一個索引。）

```bash
IDX=~/rover_rl/logs/diag/pingpong_metrics_<時間>.csv

# ① 路線圖（點雲地圖背景，四組疊同一張）
python3 scripts/plot_ablation_routes.py --index $IDX

# ② 速度變化 + 障礙淨距（曲線 + 分佈 + 統計表 csv/md/tex）
python3 scripts/plot_ablation_metrics.py --index $IDX

# ③ SR / TO / CR 對比表（csv/md/tex）
ros2 run rover_rl_inference pingpong_report $IDX --out ~/paper/tables
```

### ① 路線圖 — `plot_ablation_routes.py`

軌跡取 diag CSV 的 `map_x/map_y`（TF `map→base_footprint`），與 NDT 點雲同屬 map frame
可直接疊。只取 `pose_src=tf` 的列——NDT 沒在跑時退化的 odom 座標疊到地圖上是錯的。

| 指令 | 產出 |
|---|---|
| `--index $IDX` | 四組軌跡疊點雲地圖，各組固定配色 + ○起點 □終點 |
| `--index $IDX --speed --speed-col cmd_v` | 每演算法一張子圖，軌跡**依速度上色**（空間分布） |
| `--index $IDX --map grid` | 背景換 2D 佔據地圖（黑白印刷較乾淨）；`--map none` 純軌跡 |

### ② 速度與淨距 — `plot_ablation_metrics.py`

橫軸預設是**路徑進度 0~1** 而非時間：每段 leg 長度與耗時都不同，按時間疊圖會讓走得久的
那組被拉長、看起來像行為不同，其實只是慢。每組畫「個別 leg 細線 + 中位數粗線 + IQR 帶」，
避免十幾條線糊成一團。`--x time` / `--x dist` 可看原始時間或里程。

產出三樣：
- `ablation_speed_<stamp>.png` — 線速度 v、角速度 ω 沿路徑進度
- `ablation_clearance_<stamp>.png` — 動態障礙淨距 `min_sep` + 前方 LiDAR 距離 + 各組淨距箱型圖
- `ablation_metrics_<stamp>.{csv,md,tex}` — 統計表，欄位：

| 欄 | 意義 |
|---|---|
| `v_mean` / `v_max` | 平均（只算 \|v\|>0.05 的移動中樣本，避免等待段拉低）/ 最大速度 |
| `dv_dt_rms` / `dw_dt_rms` | **速度變化量**：\|dv/dt\|、\|dω/dt\| 的 RMS，越大代表加減速/轉向越劇烈 |
| `w_rms` | 角速度 RMS（總轉向量） |
| `sep_min` / `sep_mean` / `sep_p5` | **與障礙最近/平均/P5 淨距**（`min_sep_m` = 車體表面↔行人表面，**0 = 接觸、負值 = 重疊**） |
| `front_min` / `front_mean` | 前方 LiDAR 最近/平均距離（含牆等靜態） |
| `collision_ratio` | 接觸 tick 佔比 |

速度來源 `--speed-col` 預設 `act_v`（底盤實測，四組都有）；`cmd_v`=送出指令、
`rl_v`=RL 意圖（只有 RL 組有，其他組會自動退回 `act_v`）。

### ③ SR / TO / CR — `pingpong_report`

每段 leg 的成功/超時/碰撞分類彙整成論文對比表，同時輸出終端表格、csv、Markdown、
LaTeX booktabs（可直接 `\input`）。分組鍵 = `(experiment_tag, model)`。

## 踩過的坑（都已修，但換人接手容易重犯）

1. **`pid_vo` + `enable_vo:=false` → 靜默死路。** `path_following` 被 remap 去發
   `/rover_rl/cmd_vel_baseline_desired`，但 VO 沒啟動、沒人轉發到 `/input/nav_cmd_vel`
   → 整條鏈斷掉，**車完全不動而且不報錯**。而 `deploy_rl*` 預設帶 `enable_lvdot:=false`、
   `enable_vo` 又跟隨它 → 很容易踩到。
   修法：選 `controller=pid_vo` 即視為要 VO，無視 `enable_vo`。要純 PID 請用 `controller:=pid`。

2. **往返測試會永遠卡在「就緒」。** 空白鍵是 `status_tui` 攔截後發的，baseline 不跑 TUI
   → 沒人能按。修法：`controller!=rl` 時 `pingpong_auto_continue` 預設改為 `true`。

3. **`lidar_preprocessor` 不能只在 rl 啟動。** `diag_logger` 用 72-bin sweep 算
   `lidar_collision`（<0.5m 判碰撞）與 `leg_min_sweep_m`——那是 **SR/TO/CR 碰撞率的來源**，
   關掉等於 baseline 沒有碰撞指標。

4. **baseline 的 `front_m` / `act_v` / `sent_v` 原本會整段空白。** 這幾欄只在
   `/rover_rl_policy/status` 有值時才填，baseline 沒有 policy_node → 「速度 vs 障礙距離」
   的 X 軸與三層速度報告全做不出來，**而且要跑完才會發現**。
   修法：`diag_logger._cb_sweep` 自己從同一份 sweep 算方向扇區（切法與 `policy_node` 一致，
   2000 組隨機值比對過）；`act_*` 取 odom、`sent_*` 取 cmd_vel。
   `rl_*` **刻意留空**——baseline 沒有「RL 意圖」這一層，填了會造成誤解。

5. **`pid_vo` 的靜態障礙原本沒人擋。** `vo_safety_node` 開頭就寫明「靜態仍由 RL 的 LiDAR sweep 擋」
   ——VO 從設計上只管動態障礙。PID 零避障 + VO 只管動態 → 牆和家具完全沒人負責，
   且 `front_m` 因無 policy status 而失效、連 0.5m 硬停都沒有。
   修法：`vo_safety_node` 在 status 逾時時直接訂閱 `/rover_rl/lidar_sweep_72` 還原
   `front/left/right/back_m` 與 `front_block_ratio`，補回前方 LiDAR 安全煞。
   status 新鮮時直接讓位 → **RL 路徑行為不變**。

6. **`pingpong_test` 沒有 policy_node 會卡死。** 它的姿態/速度/mode 全從
   `/rover_rl_policy/status` 解出來，拿不到就永遠停在待命。
   修法：新增 `require_policy_status` 參數，`false` 時改走 TF + `/odom`，
   `mode` 視為恆 `nav`、`nav_type` 恆 `path`（避免誤觸發路徑遺失重規劃）。

7. **出圖兩個坑**：① 配色查表若用 `split("_")[0]`，`pid_vo` 會被當成 `pid` 拿到同色，
   圖上分不出來 → 改為由長到短比對前綴。② matplotlib 預設無中文字型，而 Noto CJK 是
   `.ttc` 集合檔、只註冊第一個 face → 系統裝了 TC 卻只認得 `Noto Sans CJK JP`
   （同一份完整字集，繁體照樣有），候選清單必須含 JP 名稱否則誤判成沒字型。

8. **🔴 三個 planner 都不 arm 就完全不動，而且不報錯（2026-09-16 發現）。**
   `dwa_planner.cpp:205/327`、`path_following.cpp:214/358`、`mppi_planner.cpp:414` 三者
   都是 `action_flag_ = false` 開機，控制迴圈開頭直接 `return`
   → **不呼叫 `planner_function*` service，一個 cmd_vel 都不會發，log 也不吭聲**。
   原本整個 rover_rl repo 沒有任何地方呼叫它 → 09-14 寫的三組 baseline 其實一次都沒真的跑起來過
   （`logs/diag/` 最新資料停在 08-24，全是 RL）。
   更陰的是這個 service 會**覆寫** launch `parameters` 裡設的值：
   ```cpp
   max_linear_velocity_     = req->speed_parameter.linear.x;    // dwa:1179 / pid:1035
   max_angular_velocity_    = req->speed_parameter.angular.z;
   enable_costmap_obstacle_ = req->obstacle_avoidance.data;
   ```
   → 就算有呼叫，漏帶 `speed_parameter` 上限會變 0，車照樣不動；
   **「統一速度上限 v=1.0/ω=1.2」的真正生效點是 `baseline_arm`，不是 launch 的 parameters 區塊**
   （那份只在 service 呼叫前短暫生效），兩邊數字必須一致。
   修法：新增 `rover_rl_inference/baseline_arm` 節點（`deploy_full.launch.py` Part 11e，
   `controller!=rl` 自動啟），訂閱 `/global_path`，在「首次拿到路徑」與「終點換位置」時 arm。
   用終點位移當判據而不是每則都 call，因為 `routing_to_path` 是 2Hz 無限 republish，
   重複 call 會重置 `path_following` 的加減速 step 造成頓挫。
   `mppi_planner.cpp:466` 到終點會自我 disarm，往返測試下一段終點換到對向點 → 同一條規則自動 re-arm。
   `rover_rl_stop.sh` / `deploy_full_stop.sh` 也要清 `baseline_arm`，它殘留會把殘留的 planner
   重新 arm 成第二個 cmd_vel 來源。

## 為什麼是 MPPI 而不是 TEB（2026-09-16 決策）

車上確實有 `rover2_ws/src/campusrover_navigation/.campusrover_teb`，但它是 **ROS 1**
（`buildtool_depend: catkin` + `roscpp`），而且只是 268K 的 wrapper 殼；目錄名前面的 `.`
就是讓 colcon 跳過。ROS 2 Humble **沒有官方 `teb_local_planner`**（apt 查無），
要自己 port g2o + costmap_2d 適配。

而 `mppi_planner` 就躺在 `dwa_planner.cpp` / `path_following.cpp` 旁邊的同一個
`campusrover_move` package，原生就訂閱 `global_path` + `costmap` + `odom` 並發 `cmd_vel`，
`config/mppi_planner.yaml` 是實車調過的正式參數 → 幾乎零移植成本。
論文分類上 TEB 與 MPPI 同屬 optimization-based local planner，加 TEB 也是同一格。

⚠ **`controller:=mppi` 跟 `enable_mppi:=true` 是兩回事，別搞混**：
後者是 `mppi_static_guard.yaml` 的三層協作模式（吃 RL 的 `reference_cmd`、不吃 `global_path`），
只在 `controller=rl` 時啟用。記憶裡「MPPI 避障弱 / 對稱正面牆僵局」那些觀察都是 static_guard
模式下的，cost 結構與原生 path 模式完全不同，**不能直接套用到 baseline 的預期上**。

`mppi_baseline.yaml` 相對原版只改兩項（都在檔案內原地註明）：
`vx_max: 0.6 → 1.0`（統一上限，否則「誰先到」沒意義）、
`enable_dynamic_obstacle_critic: true → false`（該 critic 吃 `campusrover_msgs/DynamicObstacleArray`，
車上 LV-DOT 發的是 `onboard_detector/DynamicObstacleArray`，**型別不相容接不上**，
關掉後與 dwa 同條件：都只吃 costmap 靜態障礙）。

## 尚未處理

- **VO 的 goal 導向項**（讓它會「繞」而非只「停」）同樣來自 policy status，`pid_vo` 下退化成
  「純貼近 PID 指令」。要補得把 SubgoalSelector 複製進 vo_safety，範圍較大；屬行為差異非安全問題。
- `deploy_baseline_shell` 的前景是純文字狀態行，不是 `status_tui`（後者欄位幾乎全來自
  policy status，baseline 會整片空白）。

## 安全

`pid`（已移出矩陣，但 `controller:=pid` 命令列仍可啟動）是**刻意零避障**的對照組，
不會為任何障礙物減速或轉向——要跑它務必架空確認方向、淨空場地、遙控器隨時待命。
`pid_vo` 的靜態防護只有補上的前方 0.5m 硬停（**停，不是繞**），不是完整靜態避障；
它的 VO 只對動態障礙有預測能力，這正是它在行人場景才有意義的原因。
