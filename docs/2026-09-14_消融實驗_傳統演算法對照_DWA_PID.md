# 消融實驗：傳統演算法（DWA / PID）對照 RL policy

> 建立 2026-09-14。目的：論文消融實驗——比較各演算法**在相同 A↔B 往返點位的行駛路線與速度變化**。
> 分支 `baseline-ablation-dwa-pid`。

## 設計原則：只換控制器，其餘完全相同

四種條件共用同一套 NDT / costmap / routing / LV-DOT / diag_logger / pingpong_test，
**只換「誰在發 `/input/nav_cmd_vel`」**，確保比較公平（同 TF、同地圖、同測試協定、同記錄管線）。

演算法本身**不是新寫的**，是 `campusrover_move` 裡早就在這台車跑過的既有節點：

| controller | 節點 | 行為 |
|---|---|---|
| `rl`（預設） | `policy_node` | 現況，可疊 MPPI / VO / ORCA / Recovery |
| `dwa` | `campusrover_move/dwa_planner` | 軌跡取樣 DWA + costmap 靜態避障 |
| `pid` | `campusrover_move/path_following` | 純路徑跟蹤，**關掉所有避障**（論文原始對照組） |
| `pid_vo` | `path_following` → `vo_safety_node` | 純跟蹤 + VO 動態避障 |

- 速度上限統一為底盤真實值 **v=1.0 m/s、ω=1.2 rad/s**（非 RL 訓練值 2.0，也非 DWA 舊保守值 0.5）
- 非 `rl` 時 `policy_node`/`bev`/`mppi`/`orca`/`recovery` 一律不啟，避免搶發 cmd_vel
- `lidar_preprocessor` **所有 controller 都啟**（理由見下方「踩過的坑」#3）

## 啟動與操作

```bash
net                     # 先確認 ros2 topic list 有輸出（zenoh hub 在 192.168.3.13）
# Terminal 1: 底盤 driver    Terminal 2: VLP-16 driver
deploy_baseline_shell   # 互動選單，一路 Enter 即可
```

選單四題：controller／experiment_tag 場景後綴／往返測試 A-B 點／是否錄 bag（可選含點雲）。
會自動偵測 NDT 與 LV-DOT 是否已在跑，沒跑會問要不要一併啟。

RL 那組用原本的 `deploy_rl_shell`（含 checkpoint 選單 + curses TUI）。
**四組務必用同一組 A/B 點位**，否則路線無從比較。

跑法：手動把車開到 A/B 任一點停穩 → 自動出發 → 到點自動折返（baseline 為全自動模式）→
趁停在點上的空檔重擺障礙物。`Ctrl+C` 收棧。

## 踩過的坑（都已修，但換人接手容易重犯）

1. **`pid_vo` + `enable_vo:=false` → 靜默死路。** `path_following` 被 remap 去發
   `/rover_rl/cmd_vel_baseline_desired`，但 VO 沒啟動、沒人轉發到 `/input/nav_cmd_vel`
   → 整條鏈斷掉，**車完全不動而且不報錯**。而 `deploy_rl*` 預設帶 `enable_lvdot:=false`、
   `enable_vo` 又跟隨它 → 很容易踩到。
   修法：選 `controller=pid_vo` 即視為要 VO，無視 `enable_vo`。要純 PID 請用 `controller:=pid`。

2. **往返測試會永遠卡在「就緒」。** 空白鍵是 `status_tui` 攔截後發的，baseline 不跑 TUI
   → 沒人能按。修法：`controller!=rl` 時 `pingpong_auto_continue` 預設改為 `true`。

3. **`lidar_preprocessor` 不能只在 rl 啟動。** `diag_logger` 用 72-bin sweep 算
   `lidar_collision`（<0.5m 判碰撞）與 `leg_min_sweep_m`——那是 **SR/TO/CR 碰撞率的來源**，
   關掉等於 baseline 沒有碰撞指標。

4. **baseline 的 `front_m` / `act_v` / `sent_v` 原本會整段空白。** 這幾欄只在
   `/rover_rl_policy/status` 有值時才填，baseline 沒有 policy_node → 「速度 vs 障礙距離」
   的 X 軸與三層速度報告全做不出來，**而且要跑完才會發現**。
   修法：`diag_logger._cb_sweep` 自己從同一份 sweep 算方向扇區（切法與 `policy_node` 一致，
   2000 組隨機值比對過）；`act_*` 取 odom、`sent_*` 取 cmd_vel。
   `rl_*` **刻意留空**——baseline 沒有「RL 意圖」這一層，填了會造成誤解。

5. **`pid_vo` 的靜態障礙原本沒人擋。** `vo_safety_node` 開頭就寫明「靜態仍由 RL 的 LiDAR sweep 擋」
   ——VO 從設計上只管動態障礙。PID 零避障 + VO 只管動態 → 牆和家具完全沒人負責，
   且 `front_m` 因無 policy status 而失效、連 0.5m 硬停都沒有。
   修法：`vo_safety_node` 在 status 逾時時直接訂閱 `/rover_rl/lidar_sweep_72` 還原
   `front/left/right/back_m` 與 `front_block_ratio`，補回前方 LiDAR 安全煞。
   status 新鮮時直接讓位 → **RL 路徑行為不變**。

6. **`pingpong_test` 沒有 policy_node 會卡死。** 它的姿態/速度/mode 全從
   `/rover_rl_policy/status` 解出來，拿不到就永遠停在待命。
   修法：新增 `require_policy_status` 參數，`false` 時改走 TF + `/odom`，
   `mode` 視為恆 `nav`、`nav_type` 恆 `path`（避免誤觸發路徑遺失重規劃）。

7. **出圖兩個坑**：① 配色查表若用 `split("_")[0]`，`pid_vo` 會被當成 `pid` 拿到同色，
   圖上分不出來 → 改為由長到短比對前綴。② matplotlib 預設無中文字型，而 Noto CJK 是
   `.ttc` 集合檔、只註冊第一個 face → 系統裝了 TC 卻只認得 `Noto Sans CJK JP`
   （同一份完整字集，繁體照樣有），候選清單必須含 JP 名稱否則誤判成沒字型。

## 尚未處理

- **VO 的 goal 導向項**（讓它會「繞」而非只「停」）同樣來自 policy status，`pid_vo` 下退化成
  「純貼近 PID 指令」。要補得把 SubgoalSelector 複製進 vo_safety，範圍較大；屬行為差異非安全問題。
- `deploy_baseline_shell` 的前景是純文字狀態行，不是 `status_tui`（後者欄位幾乎全來自
  policy status，baseline 會整片空白）。

## 安全

`pid` 是**刻意零避障**的對照組，不會為任何障礙物減速或轉向。第一次跑務必架空確認方向，
實跑時遙控器隨時待命。`pid_vo` 的靜態防護只有上面補的前方 0.5m 硬停，不是完整靜態避障。
