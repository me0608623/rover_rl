# SA4-R2 (c6400) vs SA4-R3 (it50) 速度與整體表現分析

> 資料範圍：2026-08-17、08-18、08-19、08-21、08-24 共 5 天，77 段有效 diag 段落
> （R2 24 段、R3 53 段）。場景皆為 ITC 3F 走廊 pingpong，測試期間走廊上有人走動。
> **不是控制良好的對照實驗**：`speed_rate` / VO 開關 / 路線在各天不完全相同，見文末限制。
> 延續並擴充既有 `2026-08-17_速度變化量與位姿guard_給PC訓練端.md` §7 的比較方法論。

## 1. 全樣本總表

| 指標 | SA4-R2 (c6400) | SA4-R3 (it50) |
|---|---|---|
| 樣本 | 24 段 / 830s / 437m | 53 段 / 2357s / 1242m |
| 實測均速（絕對值） | 0.45 m/s | 0.46 m/s |
| **ω 跟隨率**（實測 ω ÷ 送出 ω） | **66%** | **79%** |
| SUCCESS | 29% (7/24) | 19% (10/53) |
| TIMEOUT | 0% | 11% (6/53) |
| COLLISION（段級判定） | 46% (11/24) | 62% (33/53) |
| 撞牆幀數（`lidar_collision`） | 0（全程 829s） | 0（全程 2340s） |
| 動態障礙碰撞幀占比（`collision`，人） | 2.4% | 2.5% |

**兩顆模型全程沒撞過牆**，段級 COLLISION 判定全部來自動態障礙（人）欄位，逐幀占比幾乎一樣
（2.4% vs 2.5%）。走廊上一直有人走動，段級判定比例偏高，但這個欄位可能含追蹤框膨脹的假陽性，
不完全等於物理接觸，需人工核對。

絕對均速兩者幾乎一樣，但測試用的 `speed_rate` 差很多（R2 常跑 0.7~1.0，R3 常跑 0.6~0.8），
要看「速度預算利用率」才準：

| rate | R2 均速 / 利用率 | R3 均速 / 利用率 |
|---|---|---|
| 0.6 | — | 0.44 / 73% |
| 0.7 | 0.46 / 66% | 0.49 / 70% |
| 0.8 | 0.47 / 59% | 0.42 / 53% |
| 1.0 | 0.35 / **35%** | — |

R2 開越快、利用率掉越多（1.0 時僅 35%），R3 在各 rate 下相對穩定（53~73%）。跟 ω 跟隨率
（66% vs 79%）合看，方向與 8/17 文件一致：**R2 底盤實際轉不到 policy 想要的角速度，policy
誤判「還沒轉夠」又加碼下指令，把速度預算耗在來回修正上，不是耗在往前開**。

## 2. guard 分級修復前後對比（本輪對話新發現，已依「停頓原因」拆分並更正分界點）

**分界點更正**：一開始用「日期」切分（8/17-19=前、8/21+8/24=後）是錯的——8/21 那批資料
實際上還是舊版一律硬停行為（guard 分級的程式碼是同一輪對話中途才寫好並 commit
`83a082c`，8/21 16:52 那次 run 用的是舊版）。改用**該段對應的 deploy log 裡有沒有出現
`guard[soft]` 字樣**當分界（有 = 真正跑到分級後的版本），逐一核對後：8/17、8/18、8/19、
**8/21 全部都是修復前**，只有 8/24 是修復後。

同時把「停頓」拆成三類：**guard/NDT 硬停**（真正的走走停停 bug）、**VO 讓人**（安全層因
動態障礙禮讓，正常行為）、**其他/未分類**（時間窗內找不到對應 WARN，多半是到站/換 leg 等
正常減速，未逐筆人工核對）。拆分方法：偵測到 `\|sent_v\|<0.05` 且持續 ≥0.4s 的事件後，回頭
比對事件時間窗 ±1.0s 內對應 deploy log 是否有 `位姿跳變 guard` 或 `VO 全堵死`/`前方煞`/
`VO 介入` 字樣（77 段全部自動化重跑，非僅抽樣）。

| | 修復前（無 soft） | 修復後（有 soft，僅 8/24） | 變化 |
|---|---|---|---|
| **R2 guard/NDT 硬停** | 29 次 / 604s = **2.88 次/分** | 0 次 / 226s = **0.00 次/分** | **↓100%** |
| **R3 guard/NDT 硬停** | 58 次 / 1888s = **1.84 次/分** | 2 次 / 470s = **0.26 次/分** | **↓86%** |
| R2 VO 讓人 | 0 次/分 | 0.53 次/分 | — |
| R3 VO 讓人 | 0.64 次/分 | 0 次/分 | — |

**guard/NDT 造成的硬停，兩顆模型修復後都大幅下降**，R2 在這批樣本裡甚至完全歸零。VO 讓人
次數修復前後沒有一致方向（本來就跟走廊人流量有關，不是 guard 的事），列出來只是確認拆分後
兩類數字沒有互相污染。這是走走停停修復生效的直接實證，比第一版（未拆分停頓原因）的結論更
可信。

## 3. rate=0.7 頭對頭比較（回應現場「R2 感覺比較溫和」的主觀印象）

操作者在 2026-08-24 實測 R2 @ rate=0.7 時，主觀感覺行為比 R3 溫和。用同一 rate 的兩批資料
直接比對轉向平順度指標（定義沿用 8/17 文件 §7.4）：

| 指標 | R2 @0.7（10段/364s） | R3 @0.7（19段/727s） |
|---|---|---|
| \|ω\| 送出均值（占上限%） | 0.434 rad/s (52%) | 0.434 rad/s (52%) |
| ω 跟隨率 | 75% | 80% |
| **ω 飽和**（送出值 ≥95% 上限）時間占比 | **26.3%** | **29.5%** |
| **急甩**（單步角加速度打滿且變號） | **10.39 次/分** | **10.81 次/分** |
| 大幅翻轉（\|ω\|>50%上限時變號） | 0 | 0 |
| **停頓次數** | **0.99 次/分** | **0.41 次/分** |
| 朝向誤差平均 | 35.6° | 33.9° |

**ω 平順度指標本身中性**：ω 飽和時間（26.3% vs 29.5%）與急甩頻率（10.39 vs 10.81 次/分）
R2 略低，送出的 \|ω\| 平均值兩者完全相同（0.434 rad/s），這部分數字兩者接近、無明顯差異。

「停頓次數 R2 是 R3 的 2.4 倍」這條原本被解讀成「跟溫和印象矛盾」，但「停頓」欄位當時沒有
拆開原因（見 §2 方法說明：只偵測 `\|sent_v\|<0.05` 持續 ≥0.4s，不管背後成因）。用 §2 同一套
自動化方法，把 rate=0.7 這批資料**限定在「修復後（僅 8/24，對應操作者實際體驗的那次）」**
重新拆分（rate=0.7 但落在修復前的段落，例如 8/19 的資料，來自 guard 尚未分級的舊版行為，
會混淆「今天實際感受到的版本」，故排除）：

| 停頓原因 | R2 @0.7 修復後（今天 7 段/226s） | R3 @0.7 修復後（今天 9 段/345s） |
|---|---|---|
| **guard/NDT 造成**（走走停停 bug） | **0 次（0.00/分）** | **1 次（0.17/分）**（soft 連續修正 10 拍後升級硬停） |
| VO 安全層讓人（有人靠近，正常行為） | 2 次（0.53/分） | 0 次 |
| 其他/未分類 | 1 次 | 0 次 |

拆開並限定在同一版本後結論反過來：**今天這批 R2@0.7 資料裡沒有任何一次 guard/NDT 造成的
莫名凍結，R3 反而中了一次**；R2 的停頓多數是 VO 因為有人走近而禮讓煞車——這是安全層該做的
事，一般不會被感受成暴躁，會被感受成頓挫的是「無緣無故凍結又慢慢加速」這種 guard 硬停。
**現場「R2 比較溫和」的印象，拆開後其實有資料支持**，原本的統計方法把兩種性質完全不同的
事混在一起算，又把修復前後的資料混在同一個 rate 桶裡比，才顯示成相反的結論。

**方法侷限**：guard/VO 分類用「停頓事件時間窗 ±1.0s 內，deploy log 是否出現對應 WARN
文字」自動比對，77 段全部跑過（非抽樣），但比對窗口是啟發式的，個別事件仍可能誤判（例如
`diag_20260824_160539` 有一次停頓被分進「其他」而非人工核對出的 VO——時間窗邊界誤差，
不影響整體結論方向）。「其他/未分類」多半是到站或換 leg 的正常減速，未逐筆人工核對。

## 4. 結論與限制

1. R3（it50）在轉向跟隨、速度利用率上整體優於 R2（c6400），方向與既有文件（PC 端 sim
   gate：R2 過 corridor longitudinal、R3 過 nav_native）沒有矛盾。
2. **guard/NDT 硬停（真正的走走停停 bug）修復後兩顆模型都大幅下降**（§2，77 段全部自動
   拆分：R2 2.88→0.00 次/分、R3 1.84→0.26 次/分），這部分結論可信度高，不是只驗證單一事件。
3. rate=0.7、限定修復後版本的現場頭對頭（§3）：轉向平順度指標非常接近；表面的「停頓次數
   R2 較高」在拆開原因、排除混入舊版資料後其實反過來支持「R2 較溫和」的印象——R2 今天這批
   資料 0 次 guard/NDT 硬停，R3 反而中了 1 次。但這只是同一天 16 段（226s + 345s）樣本，
   還沒被更大規模驗證，不能直接推廣成「R2 全面比較溫和」的整體結論。
4. 這不是控制良好的對照實驗——rate、VO、路線都不固定，樣本分布也不均勻（R3 樣本數是 R2
   的兩倍多）。TIMEOUT 只出現在 R3，但這很可能是路線設定（更多頂到 59.6s 上限的長段）而非
   模型本質差異。
5. 要做真正公平的比較，需要固定 speed_rate、固定 VO、同路線、每顆模型跑夠的段數，且最好
   同一天測試以控制環境變數（人流量）。

## 附錄：重現方式

資料來源：`~/rover_rl/logs/diag/diag_*/`（`*_params.json` 標記各段使用的 model / rate /
vo_enabled；`*.csv` 為 20Hz 逐拍紀錄）。

```bash
# 段級結果（SUCCESS/TIMEOUT/COLLISION）與最終距離，從對應 deploy log 抓取：
grep -A1 "本段結果" ~/rover_rl/logs/deploy_<時間戳>.log

# 逐段指標計算邏輯（本文件用的臨時腳本，非常設工具）：
#   距離：map_x/map_y 逐拍歐氏距離累積
#   均速：act_v 絕對值平均（實測值，非送出值）
#   ω 跟隨率：mean(|act_w|) / mean(|sent_w|)
#   停頓：|sent_v| < 0.05 且連續 ≥0.4s 的區段數
#   急甩/ω飽和：用 rl_w（policy 每次真正的決策，需先去重複值）逐次變化點計算，
#     不能直接拿 diag CSV 20Hz 逐列相減（那是取樣點不是決策點，會得到荒謬的高頻假訊號）
#   停頓原因拆分（guard/NDT vs VO vs 其他）：
#     1. 每個 diag 資料夾對應到某個 deploy log 裡「▶ 開始實驗 '<name>'」到下一個同類
#        訊息（或檔尾）之間的行區間
#     2. 該區間內抓所有帶時間戳的 WARN：符合 `位姿跳變 guard\[(\w+)\]` 記為 guard 事件，
#        符合 `VO 全堵死|前方煞|VO 介入` 記為 VO 事件
#     3. 每個停頓事件（CSV 算出的 t_wall 起訖）±1.0s 內若命中 guard 事件優先記 guard，
#        否則命中 VO 記 VO，都沒有則記「其他」
#   修復前/後分界：不能用日期，要用該段對應 deploy log 裡有沒有出現 `guard[soft]`
#     字樣（有 = 已跑到分級後版本）——8/21 資料所屬的 run 沒有 soft，仍屬修復前

# 標準三層速度/延遲分析（單段）：
ros2 run rover_rl_inference analyze_diag ~/rover_rl/logs/diag/diag_<時間戳>/diag_<時間戳>.csv
```
